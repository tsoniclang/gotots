# Normative Translation And TSTS Output Contract

Status: normative. This document defines the TypeScript product that GoToTS
must generate from the declared TS-Go corpus. The pinned typed census is the
source authority; generated TypeScript, reports, and tests must agree with it.

## Translation Proof Unit

Every translated declaration and body has one source-linked proof record:

```text
canonical Go identity
  -> selected Go declaration and signature
  -> typed body operations and evaluation order
  -> representation requirements and selected static representations
  -> lowering plan
  -> generated TypeScript declarations and statements
  -> semantic, staticness, and performance evidence
```

The record contains source revision, package, file, declaration identity,
source span, signature hash, body-semantic hash, representation plan hash,
generated file and symbol, extension seam identities, external obligations,
and manual-body ownership when applicable. A missing stage blocks publication.

Generated output is not accepted merely because TypeScript parses or existing
tests pass. The proof record and independently computed completeness ledgers
must account for every selected source unit and operation.

## TSTS Product Layers

The generated TSTS product has four disjoint ownership roots:

1. **Generated compiler core.** GoToTS owns TS-Go declarations and bodies.
2. **Generated language ABI and external contracts.** GoToTS owns Go-language
   semantic carriers/intrinsics and exact external declaration stubs.
3. **Manual bodies.** Reviewed declaration-owned implementations satisfy the
   manual-body contract and live outside generated roots.
4. **TSTS product extensions.** The extension host, facts, observations,
   providers, public extension API, and product assembly are separately owned
   TSTS source, composed through generated typed seams.

Generation starts with empty generated roots. No generated file is edited by a
later merge step. Manual, extension, and external-emulation roots are never
generator output. A path ownership collision blocks publication.

The logical layout is normative even when package integration chooses different
physical root names:

```text
generated/
  core/                     translated TS-Go compiler packages
  schema/                   schema-derived AST kinds, nodes, unions, factories
  language-abi/             Go language carriers and static intrinsics
  external-contracts/       exact imported-package declaration obligations
  extension-core-contract/  typed bridge implemented by TSTS product source
product/
  extensions/               TSTS host, facts, observations, providers
  assembly/                 public exports, compiler session, CLI integration
manual-bodies/              explicit declaration-owned implementations
```

External emulation implementations are a separate product input. They do not
share the generated external-contract root. Package exports may present a
stable public layout, but the ownership manifest always maps each public path
to exactly one root above.

## Output Envelope

Generated TypeScript must be:

- strict ESM with explicit `.js` relative imports;
- accepted by the selected TS-Go/TSTS schema-level frontend contract;
- statically analyzable by Tsonic and suitable for C# and Rust lowering;
- deterministic in file layout, import ordering, declaration ordering, names,
  helpers, formatting, provenance, and source maps;
- free of CommonJS, triple-slash references, `eval`, generated functions,
  proxies used for language semantics, and reflective member discovery;
- free of `any`, unchecked `unknown` recovery, string-selected source members,
  runtime type-name dispatch, and source-name semantic tables;
- free of cast-based compiler-state writes and substitute side tables where
  TS-Go stores the corresponding state on compiler objects;
- split into semantically named files under the repository file-size policy.

Type assertions may express a statically proven relation that TypeScript cannot
derive. Each assertion class is represented in the lowering plan and verified;
an assertion is never a recovery mechanism for missing type evidence.

Every generated file begins with deterministic provenance. The exact JSON
schema is versioned, but it identifies at least the source revision, GoToTS
revision, project profile, generated path, and content hash:

```ts
// Code generated by GoToTS for TSTS. DO NOT EDIT.
// @gotots-generated {"schemaVersion":1,"sourceRevision":"...","profileHash":"...","path":"internal/parser/jsdoc.ts","contentHash":"..."}
```

Generated source contains the TypeScript implementation, relevant upstream
documentation, and concise provenance. It does not duplicate complete Go
bodies as comments. Full source linkage belongs in source maps and proof
records so runtime parsing, package size, and code review are not burdened by a
second textual copy of the program.

Generated expressions use ordinary static TypeScript when it is exact. Output
does not retain translation scaffolding such as unconditional non-null
assertions, casts to scalar aliases, or generic helper calls after the planner
has proved a direct operation. Conversely, readability never authorizes
removing an observable Go check or state transition.

## Package, Module, And Name Identity

Go package and object identity, not spelling, determines generated identity.
Source names are retained when they are valid and unambiguous TypeScript names.
Collisions receive deterministic identity-derived disambiguation. File layout
never changes symbol identity.

Generated internal names are not a product API. Separately owned TSTS modules
depend on a generated, narrow extension-core contract instead of importing
arbitrary generated internals. Public TSTS extension exports are owned by the
TSTS product layer and are checked against that generated contract.

Go receiver methods may become TypeScript methods or statically named
functions. One consistent choice is made per declaration family from identity,
effects, addressability, extension seams, and measured output quality. Member
spelling never selects the storage model.

## TS-Go Schema Contract

TSTS AST kinds, node fields, aliases, unions, factory order, and visitor order
come from the exact pinned TS-Go schema. GoToTS does not hand-maintain numeric
kind values or infer a JavaScript object shape from current output. Schema
generation fails on a missing, extra, reordered, or incompatible schema member.

TS-Go mutations of `Node`, `Symbol`, `Type`, `FlowNode`, `Program`, and
`EmitContext` state become central fields on the corresponding generated TSTS
types. State with a different owner requires equivalent typed storage evidence
from TS-Go or an explicit generated product contract.

Example source mutation:

```go
node.Parent = parent
symbol.Declarations = append(symbol.Declarations, declaration)
```

Required generated shape:

```ts
node.parent = parent;
symbol.declarations.push(declaration);
```

Capitalization follows the generated schema contract. The normative point is
direct central state with the same owner and lifetime. A `WeakMap` indexed by a
node ID, cast write, or string-selected field is not equivalent.

## Source Types And Storage Representations

Go source type identity remains separate from generated storage. The planner
chooses one static representation for each value-flow group and records the
proof. Runtime code never probes which representation a value happens to use.

Required representation classes include:

| Go semantic class | TSTS output requirement |
| --- | --- |
| `bool` | direct boolean semantics |
| signed/unsigned integers | explicit width, conversion, shift, and observable overflow semantics |
| floating point | exact selected width, NaN, infinity, signed-zero, and conversion behavior |
| string | Go UTF-8 byte/rune semantics where observed; direct JS string only where equivalent |
| pointer to heap object | direct object identity, plus `undefined` only when nil is possible |
| addressable scalar/header/field | elided reference when nonescaping; otherwise typed static storage reference |
| array `[N]T` | fixed length and Go value-copy behavior |
| slice `[]T` | direct array only under complete proof; otherwise nilable backing/offset/length/capacity view |
| map `map[K]V` | nil behavior, Go key equality/hash, zero result, comma-ok, and iteration contract |
| struct value | Go copy and zero semantics, not accidental JavaScript reference aliasing |
| interface | direct/devirtualized form when closed; typed dynamic carrier when identity/assertion behavior is observed |
| function | callable identity plus nilability, receiver capture, variadic, and multi-result behavior |
| channel | exact send/receive/close/select behavior for selected corpus uses |
| external named type | generated exact declaration/stub obligation; no library behavior in GoToTS |

## Worked Translation Shapes

The following examples are normative for semantic decisions and static output
shape. Helper spellings belong to the versioned generated language ABI and are
pinned once selected. Equivalent output is acceptable only when its proof
record establishes every listed behavior.

### Exact Integer Operation

Go input:

```go
func add(a int32, b int32) int32 {
    return a + b
}
```

Typed decision: operands and result are `int32`; observable overflow wraps to
32 signed bits. Required TypeScript shape:

```ts
export function add(a: GoInt32, b: GoInt32): GoInt32 {
  return goInt32(a + b);
}
```

Range proof may remove a conversion only for a specific operation whose result
cannot escape the `int32` range. The proof is attached to that operation.

### Parser Pool With `defer`

Go input representative of TS-Go parser code:

```go
p := getParser()
defer putParser(p)
p.initializeState(sourceFile)
return p.parse()
```

Required TypeScript control-flow shape:

```ts
const parser = getParser();
try {
  parser.initializeState(sourceFile);
  return parser.parse();
} finally {
  putParser(parser);
}
```

All return, panic, and nested-defer paths execute cleanup in Go order. A call
placed after the translated body without `finally` is not equivalent.

### Simple Slice Flow

Go input:

```go
func first(values []Node) *Node {
    return values[0]
}
```

When analysis proves that this flow does not observe nil versus empty,
capacity, backing identity, reslicing, append reuse, or element address, a
native array is permitted:

```ts
export function first(values: readonly Node[]): Node {
  return values[0]!;
}
```

The bounds proof is explicit. Without it, the selected language ABI performs
the Go bounds panic before the load.

### Nil And Empty Slice Result

Go input:

```go
func collect(enabled bool) []Node {
    if !enabled {
        return nil
    }
    return make([]Node, 0)
}
```

Nil and non-nil empty are distinguishable by Go operations and interfaces. A
direct representation may use `undefined` for nil and `[]` for non-nil empty:

```ts
export function collect(enabled: boolean): Node[] | undefined {
  if (!enabled) return undefined;
  return [];
}
```

This form is permitted only while every operation consuming the value preserves
the distinction. It does not authorize treating every slice as `T[]`.

### Aliased Reslice

Go input:

```go
func prefix(values []Node, count int) []Node {
    return values[:count]
}
```

The result shares backing storage and has independent length and capacity. A
semantics-preserving static view has this shape:

```ts
export function prefix(values: GoSliceView<Node>, count: GoInt): GoSliceView<Node> {
  return values.reslice(0, count);
}
```

Mutating `values.length`, copying with `slice`, or returning an unrelated array
is forbidden. The selected view implementation must prove bounds, aliasing,
append reuse, nil handling, and element copy behavior.

### Static Address Of Field

Go input:

```go
scope := &state.Scope
*scope = next
```

When the reference does not escape, lower it away:

```ts
state.scope = next;
```

When it escapes, use a typed, statically bound reference:

```ts
const scope: GoRef<Scope> = goFieldRef(
  () => state.scope,
  (value: Scope) => { state.scope = value; },
);
scope.set(next);
```

The implementation may specialize this shape to avoid allocation. It may not
pass `"scope"`, reflect over properties, or copy the field into detached
storage.

### Multiple Assignment

Go input:

```go
a, b = b, a
```

Required evaluation shape:

```ts
const nextA = b;
const nextB = a;
a = nextA;
b = nextB;
```

All right-hand expressions are evaluated before any left-hand store, including
indexed targets, getters introduced by lowering, map operations, and pointers.

### Map Comma-Ok

Go input:

```go
value, ok := values[key]
```

Required semantic shape:

```ts
const [value, ok] = goMapLookup(values, key, zeroValueForV);
```

Missing and present-with-zero remain distinct. Nil-map lookup succeeds with the
zero value and `false`; nil-map assignment panics. JavaScript `Map.get()` alone
is insufficient because `undefined` cannot encode both outcomes.

### Struct Value Copy

Go input:

```go
copy := original
copy.Flags = next
```

For a Go value struct, output must not alias the same mutable object:

```ts
const copy = copyRecord(original);
copy.flags = next;
```

Compiler heap objects reached through pointers retain shared identity instead.
The type and flow graph, not TypeScript syntax, selects copy behavior.

### External Package Contract

Go input:

```go
var builder strings.Builder
builder.WriteString(text)
```

GoToTS emits a static import and exact generated declaration contract:

```ts
import { Builder } from "@gotots/go-stdlib/strings.js";

const builder = Builder.zero();
builder.WriteString(text);
```

The external contract records package, object, receiver, parameters, results,
effects required by callers, and unresolved implementation status. A separate
emulation package owns behavior. Product acceptance fails while a reachable
required implementation remains a placeholder.

## TSTS Extension Composition

Generated core behavior without an attached extension host must match pinned
TS-Go. TSTS product behavior is added through typed semantic seams resolved
against canonical Go declarations and operations before emission.

A generated checked-property seam has this shape:

```ts
const sourceResult = checkPropertyAccess(node, receiverType);
extensionCoreBridge.afterCheckedPropertyAccess({
  node,
  sourceResult,
  sourceSelectedSymbol,
  sourceSelectedDeclaration,
});
return sourceResult;
```

The exact bridge ABI is generated from a TSTS-owned seam specification. The
operation that selects a symbol, declaration, signature, result type, or
explicit/inferred method type argument passes that evidence directly. Product
extensions do not re-enter checker APIs to rediscover it.

Seams may observe, validate, publish facts, or provide a separately typed
target mapping according to their declared category. They never alter ordinary
core semantics implicitly. Missing, duplicate, relocated, or structurally
incompatible seams block generation. Mid-operation seams use typed semantic
anchors, not line numbers, local names, comments, or source fragments.

Compiler-state augmentation required by a product contract is generated
centrally on the owning type or represented by another explicitly reviewed
static owner. Cast writes and parallel identity tables are forbidden.

## Initialization, Cycles, And Effects

Go package initialization order is computed from package and declaration
dependencies and emitted deterministically. Runtime initializers execute once
in Go order. Type-only dependencies remain type-only imports when evaluation is
not required. An accidental JavaScript import cycle is never used as an
initialization mechanism.

Evaluation order, short declaration scope, labeled control flow, named results,
defer, panic/recover, variadics, multi-results, range-variable lifetime,
goroutines, and channel operations are explicit lowering concerns. An
unrepresented semantic effect blocks output.

## Static Output Verification

The generated tree is parsed and typechecked strictly, then structurally
scanned. Verification rejects at least:

- unresolved imports, declarations, types, or external obligations;
- `any`, unproven casts, reflective or string-selected member access;
- dynamic dispatch not justified by a typed Go interface operation;
- generated/manual ownership overlap;
- missing schema-generated nodes, fields, unions, factories, or visitors;
- side-table compiler state that disagrees with TS-Go ownership;
- CommonJS, triple-slash references, forbidden host globals, or nondeterminism;
- output outside the selected Tsonic-compilable grammar;
- files violating the semantic decomposition policy.

Two clean generations from identical inputs must produce byte-identical source,
source maps, manifests, representation plans, seam reports, manual-body reports,
external obligations, and verification evidence.
